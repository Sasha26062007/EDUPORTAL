## 1. Контекст та динаміка Спринту 3

Спринт 3 став найбільш насиченим технічним артефактом у життєвому циклі розробки та тестування «ЕдуПортал»:
- **Тест-дизайн:** Спроєктовано **30 детальних тест-кейсів** (TC-01..TC-30) із застосуванням комбінованих технік (BVA, еквівалентний поділ, Decision Table, Use Case Testing, State Transition, Error Guessing). Забезпечено 100% покриття 40 базових вимог SRS 1.1.
- **Тестове виконання (Run 1):** Проведено наскрізне виконання всіх 30 тест-кейсів у середовищі LMS v2.4-qa-rel (PHP 8.2, MariaDB 10.11, Ubuntu 22.04 LTS).
- **Результати виконання:**
  - **Passed:** 18 тест-кейсів (60.0%)
  - **Failed:** 10 тест-кейсів (33.3%)
  - **Blocked:** 2 тест-кейси (6.7%) — TC-16 (блокований BUG-007) та TC-26 (блокований BUG-010)
- **Дефекти:** Оформлено **10 вичерпних Bug Reports** (BUG-001..BUG-010) з логами, скріншотами, шарами помилок та критеріями виправлення.
- **Контроль якості та аудит:** 
  - Проведено 100% рецензування тест-кейсів та баг-репортів Скрам-майстром (Панайотов) за чеклистом 8 обов'язкових пунктів.
  - Проведено сліпий аудит Аудитором-опонентом (Кираківський) з відтворенням 3 випадково обраних дефектів (BUG-005 Critical, BUG-002 Major, BUG-004 Normal) без консультацій з автором — усі 3 успішно підтверджено (100% відтворюваність).

## 2. Аналіз за шаблоном Start / Stop / Continue

### 2.1. START (Що почати робити у Спринті 4)

1. **Автоматизація регресійного пулу тест-кейсів (API & E2E):**  
   - Усі 18 успішних тест-кейсів (TC-01..TC-03, TC-06..TC-08 тощо) повинні бути автоматизовані через Postman/Newman або Playwright/Pytest у Спринті 4, щоб скоротити час ручного прогону перед релізом.
2. **Pre-execution Sanity Check стенду:**  
   - Запровадити обов'язковий автоматичний смоук-тест тестового стенду перед початком виконання глибоких тест-кейсів, щоб уникати раптових падінь через стан бази даних (як виявлено в TC-20).
3. **Автоматична перевірка вкладень у баг-репортах:**  
   - Додати pre-commit хук або CI-чек, який валідує наявність реальних файлів скріншотів у папці ttachments/ за назвами з таблиці баг-репортів.
4. **Матриця конфігурацій (Browser Matrix Automation):**  
   - Запустити паралельне тестування на десктопних та мобільних в'юпортах (Chrome, Firefox, Safari/WebKit, Mobile Chrome).

### 2.2. STOP (Що припинити робити)

1. **Припинити використання неочевидних тестових паролів у документації:**  
   - Усі тестові облікові записи мають слідувати строгому єдиному патерну (QA-Pass-2026!), щоб уникнути плутанини між кейсами перевірки валідації та смоук-тестами.
2. **Припинити ручне дублювання статусу виконання в кількох файлах:**  
   - Статуси прогону (Pass/Fail/Blocked) повинні фіксуватися первинно в execution-log.xlsx, а в README.md збиратися скриптом генерації звітів або узгоджуватися перед коммітом.
3. **Припинити блокування пов'язаних кейсів без швидкого workaround:**  
   - Для заблокованих кейсів (TC-16 та TC-26) слід готувати тестові фікстури бази даних на випадок, якщо основна функція блокує перевірку дочірньої.

### 2.3. CONTINUE (Що працює відмінно і продовжувати)

1. **Глибока деталізація BVA (граничних значень):**  
   - Використання точних граничних пар (20.00 MB vs 20.01 MB, 5 vs 6 файлів, 3 vs 4 спроби, штраф 10% і 50%) показало виняткову ефективність і призвело до виявлення логічних дефектів (BUG-006, BUG-007, BUG-008); окремо перевірка типів файлів виявила приймання `.exe` (BUG-005).
2. **Формат баг-репортів за структурою IEEE 829 / GitHub Issues:**  
   - Повне зазначення передумов, пронумерованих кроків, очікуваного та фактичного результату, повного тексту системних помилок (PHP Fatal error, SQLSTATE[23000]) та зв'язку з SRS значно прискорює аналіз розробниками.
3. **Сліпий аудит дефектів (Auditor-Opponent Blind Reproduction):**  
   - Практика сліпого відтворення дефектів іншим учасником команди без допомоги автора довела якість оформлення баг-репортів та незалежність оцінки.
4. **Спільне володіння якістю та взаємне рецензування (Peer Review):**  
   - 100% рецензування артефактів Скрам-майстром до фінального мерджу виключає синтаксичні та змістовні помилки.
