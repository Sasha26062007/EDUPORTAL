## 1. Загальний опис та об'єкт тестування

### 1.1. Мета планування тестування
Цей документ визначає комплексну стратегію, рівні, типи (§4.12 навчальної програми), методики, критерії та ресурсне забезпечення процесів забезпечення якості для системи дистанційного навчання **«ЕдуПортал»**. План розроблено на основі скоригованої специфікації вимог **SRS 1.1** (після усунення 24 закладених дефектів вимог) та замовлення на функціонал розрахунку журналу оцінок, контролю знань і методів зарахування.

### 1.2. Об'єкт тестування
Об'єктом тестування є програмний комплекс «ЕдуПортал», що складається з двох взаємопов'язаних частин:
1. **Вебзастосунок LMS «ЕдуПортал» (демонстраційний стенд поточної версії):**
   - URL стенду: `https://sandbox.moodledemo.net` (відповідно до п. 2.2 специфікації SRS 1.1).
   - Тестові облікові записи: `admin` (Адміністратор), `manager` (Менеджер курсів), `teacher` (Викладач), `student` (Студент); пароль для всіх ролей: `sandbox24`.
   - Основний функціонал: авторизація (F-10, F-20, GUI-10, GUI-20), каталог курсів (F-30), самозарахування за кодовим словом (F-40, GUI-50, GUI-60), сторінка курсу з розділами (F-50), завдання з завантаженням файлів і онлайн-текстом (F-60, F-70, GUI-30), проходження тестування (F-80, GUI-40), форуми (F-90, GUI-80), журнал оцінок (F-100, GUI-45), профіль користувача (F-110), календар (F-120, GUI-70), створення курсів менеджером (F-130).
2. **Модуль бізнес-логіки Java 17 (`code/modules/eduportal`, пакет `ua.kpi.tzyapz.eduportal`):**
   - Технологічний стек: Java 17 LTS, Apache Maven 3.9, без зовнішніх сторонніх бібліотек runtime (лише стандартні пакети `java.time`, `java.math`, `java.util`).
   - Клас `GradeCalculator`: зважений підсумок `weightedTotal(items)`, трансляція у шкалу ECTS `ectsLetter(total)` за уточненими інтервалами BL-20 (DEF-04), штраф за запізнення `latePenalty(score, daysLate)` за BL-30 / F-60 (DEF-10).
   - Клас `QuizScorer`: розрахунок балу за питання `questionScore(question, selected)` з підтримкою часткового балу без від'ємних результатів за BL-50 (DEF-08), підсумок тесту у відсотках `score(answers, key)` за BL-60.
   - Клас `EnrollmentValidator`: перевірка умов самозарахування `canEnroll(...)`, валідація кодового слова `keyMatches(...)`, часового вікна `withinPeriod(...)`, ліміту місць `hasCapacity(...)`, пререквізитів `prerequisiteMet(...)` та формування списку точних порушень `violations(...)` за BL-80 (DEF-23).
   - Записи-DTO: `GradeItem`, `QuizQuestion`, `Student`, `Course`.

### Група 2: Тестування продуктивності та навантаження (типи 16–24)

| № | Назва типу тестування | Застосовність | Ціль (що і навіщо перевіряємо) | Опис методики перевірки | Пріоритет | Інструменти та дані |

## 4. Критерії процесів тестування

### 4.1. Критерії початку тестування (Entry Criteria)
1. Специфікація вимог SRS 1.1 затверджена командою після повного аудиту та виправлення всіх 24 дефектів.
2. Демонстраційний стенд `https://sandbox.moodledemo.net` доступний, тестові облікові записи функціонують.
3. Модуль бізнес-логіки Java збирається командою `mvn test-compile` без помилок компіляції.
4. План тестування погоджено аудитором-опонентом та затверджено керівником тестування.

### 4.2. Критерії призупинення та відновлення тестування (Suspension & Resumption)
- **Призупинення:**
  - Недоступність демонстраційного стенду понад 1 годину без можливості перезапуску.
  - Виявлення блокуючого дефекту (Blocker), що унеможливлює вхід до системи або призводить до аварійного завершення JVM.
- **Відновлення:**
  - Відновлення доступу до стенду (або планове скидання на початку години).
  - Отримання виправлення дефекту, успішний повторний прогін Smoke-тестів.

### 4.3. Критерії завершення тестування (Exit Criteria / Definition of Done)
1. 100% тест-кейсів, спроєктованих для верифікації вимог SRS 1.1, виконано та зафіксовано у звітах.
2. Не менше 95% виконаних тест-кейсів мають статус «Пройдено» (Passed).
3. Відсутні відкриті дефекти блокуючого (Blocker) та критичного (Critical) рівнів важливості.
4. Усі виявлені відхилення зареєстровані у дефект-реєстрі з повним описом кроків відтворення.
5. Матриця простежуваності «вимоги $ightarrow$ тест-кейси» покриває 100% функціональних та нефункціональних вимог.

- **Клієнтське середовище:**
