## 2. Аналіз за категоріями Start / Stop / Continue

### 2.1. Start (Що команді слід почати робити в наступних спринтах)
1. **Почати формувати тест-кейси на етапі раннього узгодження вимог (Test-Driven QA):** Складати чорнові шаблони тест-кейсів паралельно з виправленням тексту вимог у SRS 1.1, що дозволить у Спринті 3 скоротити час на розробку тестової документації на 30%.
2. **Почати вести автоматизовану матрицю простежуваності (Traceability Matrix):** Запровадити єдину таблицю прив'язки `User Story` $\leftrightarrow$ `SRS ID` $\leftrightarrow$ `Test Case ID` ще до старту написання детальних тест-кейсів.
3. **Почати проводити крос-опитування перед здачею (Mock Blitz):** Практикувати взаємні бліц-опитування за теоретичним мінімумом за 2 дні до публічного захисту для максимальної впевненості кожного учасника команди.
4. **Почати вести журнал автоматизованих перевірок (CI/CD):** Налаштувати базовий GitHub Actions workflow для автоматичної перевірки лінтингу markdown-файлів та цілісності посилань у документації.

### 2.2. Stop (Що команді слід припинити робити)
1. **Припинити використання суб'єктивних та абстрактних формулювань:** Категорично відмовитися від слів-маркерів («швидко», «зручно», «надійно», «без помилок») як у вимогах, так і в описах тестів (на цьому наголосив Аудитор-опонент під час оспорювання правок D-02 та D-08).
2. **Припинити спроби механічної перенумерації вимог:** Відмовитися від зсуву номерів після вилучення дублікатів (залишати «дірки» в нумерації з фіксацією у журналі змін), оскільки це руйнує стабільність посилань у наступних спринтах.
3. **Припинити роздування скоупу (Scope Creep):** Не пропонувати надлишкових важких зовнішніх технологій (як-от комерційний OpenAI API чи тотальний відеопрокторинг), які не передбачені бюджетом і технічним завданням замовника.
4. **Припинити відкладати зведення аркушів аудиту на останній момент:** Уникати ситуацій, коли індивідуальні аркуші надходять на зведення за 1 день до фінального релізу; зведення має відбуватися строго в середині спринту (День 5).

### 2.3. Continue (Що працювало ефективно і має бути продовжено)
1. **Продовжувати суворе дотримання правила «Двох аудиторів на розділ»:** Перехресна незалежна перевірка кожного розділу двома учасниками довела свою надзвичайну ефективність — 15 дефектів було знайдено одночасно двома аудиторами незалежно.
2. **Продовжувати інженерно обґрунтовану модерацію спорів:** Робота Аудитора-опонента як «Адвоката замовника» дозволила відфільтрувати 3 необґрунтовані правки та запобігла появі нових дефектів у специфікації SRS 1.1.
3. **Продовжувати деталізацію тест-плану під реальний demo-стенд:** Вказувати конкретні ролі (`teacher`, `student`, `admin`), реальні сутності (`GradeCalculator`, `QuizScorer`), точні числові обмеження та інструменти замість загальних фраз.
4. **Продовжувати асинхронні щоденні standup у месенджері:** Короткі звіти у форматі «зроблено / заплановано / блокери» забезпечують 100% прозорість прогресу без витрати часу на довгі дзвінки.
