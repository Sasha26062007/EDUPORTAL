## 2. Виконані інженерні задачі та результати

### 2.1. Розгортання інфраструктури та конфігурація проєкту
1. Створено робочий Maven-проєкт `qa-eduportal` на основі стартового модуля `code/modules/eduportal/v1`.
2. Налаштовано файл `pom.xml`:
   - Цільова платформа компілятора: Java 17 (`<maven.compiler.release>17</maven.compiler.release>`);
   - Залежності тестування: `org.junit.jupiter:junit-jupiter:5.10.2` та `org.seleniumhq.selenium:selenium-java:4.21.0`;
   - Налаштовано плагін `maven-surefire-plugin:3.2.5` з виключенням групи `ui` за замовчуванням (`<excludedGroups>ui</excludedGroups>`), що забезпечує швидкий автономний запуск юніт-тестів командою `mvn test`.
3. Створено файл `.gitignore` для виключення згенерованих артефактів збірки `target/` та конфігурацій IDE.

### 2.2. Запис та експорт сценаріїв у Selenium IDE
1. На демо-стенді Moodle записано 3 ключові призначені для користувача сценарії:
   - `TC-01_ValidStudentLogin`: авторизація студента `student` / `sandbox24` та валідація переходу до особистого кабінету `/my/`;
   - `TC-02_InvalidPasswordShowsError`: перевірка відображення блоку помилки автентифікації та збереження введеного логіну в полі введення (вимога GUI-20);
   - `TC-08_CourseCatalogNavigation`: перехід до навчального курсу `id=2` та верифікація заголовка "My first course".
2. Проєкт збережено у форматі `.side` (`selenium-ide/eduportal.side`).
3. Виконано експорт сценаріїв у Java JUnit 4 (`selenium-ide/export/MoodleLoginScenarioTest.java`, `selenium-ide/export/MoodleCourseEnrollScenarioTest.java`).

### 2.3. Розробка стабільних автотестів Selenium WebDriver 4 (UI)
1. Реалізовано архітектурний патерн **Page Object Model (POM)**:
   - Базовий клас `BasePage` з інкапсуляцією методів явного очікування `WebDriverWait` (`visibilityOfElementLocated`, `elementToBeClickable`, `urlContains`);
   - Спеціалізовані класи сторінок: `LoginPage`, `DashboardPage`, `CoursePage`, `CourseEnrollmentPage`, `AssignmentPage`, `GradebookPage`.
2. Розроблено 4 тестові класи у пакеті `ua.kpi.tzyapz.eduportal.ui`, що містять **11 стабільних тест-методів** (норматив $\ge 8$):
   - `MoodleLoginUiTest` (3 методи): TC-01, TC-02, TC-03;
   - `MoodleCourseEnrollmentUiTest` (3 методи): TC-07, TC-08, TC-09;
   - `MoodleAssignmentUiTest` (3 методи): TC-12, TC-15, TC-16;
   - `MoodleGradebookUiTest` (2 методи): TC-25, TC-26.
3. Забезпечено відповідність усім інженерним вимогам:
   - Обов'язковий сучасний headless-режим (`--headless=new`, `--window-size=1280,900`);
   - Виключно явні очікування (жодних `Thread.sleep` та неявних очікувань `implicitlyWait`);
   - Гарантоване закриття браузера `driver.quit()` у `@AfterEach` базового класу `BaseUiTest`, що запобігає зависанню процесів `chromedriver.exe`;
   - М'які перевірки `assertAll` для комплексної валідації властивостей сторінки.

### 2.4. Написання власної частки юніт-тестів JUnit 5
1. У класі `EnrollmentValidatorTest` розроблено **14 тестів** (норматив $\ge 3$) для правил:
   - **BL-70 (умови самозарахування):** збіг кодового слова з урахуванням регістру (`keyMatches`), перевірка дат періоду зарахування (`withinPeriod`), перевірка наявності вільних місць за місткістю (`hasCapacity`), перевірка складання передумовного курсу з порогом $\ge 60$ балів (`prerequisiteMet`), підсумкове рішення `canEnroll`;
   - **BL-80 (коди порушень):** порядок та повнота повернення кодів `KEY`, `PERIOD`, `CAPACITY`, `PREREQUISITE`;
   - Перевірка валідації `null`-аргументів через `assertThrows(IllegalArgumentException.class)`.
2. Застосовано техніку граничних значень (BVA) для точок $N-1, N, N+1$.
3. Використано параметризовані тести `@ParameterizedTest` з постачальниками даних `@CsvSource` та `@ValueSource`.

### 2.5. Виявлення та документування закладених дефектів модуля v1
Під час тестування модуля бізнес-логіки v1 інженером SDET було виявлено 2 закладених дефекти:
1. **BUG-MOD-01:** `EnrollmentValidator.withinPeriod()` ігнорує кінцеву дату періоду зарахування `enrolEnd` (перевіряє лише `!today.isBefore(enrolStart)`). Тест `withinPeriodDayAfterEndMustReturnFalse` зафіксував цей дефект (падає на v1, очікується `false`, повертається `true`).
2. **BUG-MOD-02:** `EnrollmentValidator.hasCapacity()` використовує нестрогу нерівність `<=`, дозволяючи зарахування при повній заповненості курсу ($enrolled == capacity$). Тест `hasCapacityWhenCourseIsFullMustReturnFalse` зафіксував цей дефект (падає на v1, очікується `false`, повертається `true`).

Обидва тести залишено «червоними» у тестовому наборі відповідно до методичних вказівок §4.9. Для кожного дефекту складено вичерпний звіт за стандартами Спринту 3 у каталозі `docs/defects/`.
