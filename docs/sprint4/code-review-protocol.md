## 1. Нормативна база та чек-лист рецензування (§5.3 методичних вказівок)

Відповідно до розділу 5.3 та критеріїв Definition of Done (DoD) Спринту 4, кожен тестовий клас команди пройшов ретельний перегляд за єдиним 8-пунктовим чек-листом інженерної якості:

| № | Пункт чек-листа §5.3 | Опис вимоги та критерій прийняття |
|:---:|:---|:---|
| **CR-01** | **Прив'язка до SRS та очікувані значення** | Тест перевіряє правило з BL-вимоги (або крок тест-кейсу), ID вимоги видно у `@DisplayName`. Очікуване значення вирахувано строго за специфікацією SRS, а не «підігнано» під поточний код модуля v1. |
| **CR-02** | **Структура AAA (Arrange — Act — Assert)** | У кожному тесті чітко розмежовано етапи підготовки даних, виконання дії та перевірки результату. Один тест має одну логічну причину впасти. |
| **CR-03** | **Описові назви методів** | Назва методу вичерпно описує поведінку системи (наприклад, `keyMatchesExactValueReturnsTrue`), уникаючи беззмістовних чи числових назв на зразок `test1`, `testCheck`. |
| **CR-04** | **Аналіз граничних значень (BVA)** | Граничні значення перевірено з обох боків межі ($N-\Delta, N, N+\Delta$). Для діапазонів застосовано параметризовані тести (`@ParameterizedTest` з `@CsvSource` / `@ValueSource`) замість дублювання коду. |
| **CR-05** | **Валідація винятків та точність чисел** | Винятки перевіряються виключно через `assertThrows(ExpectedException.class, ...)`. Порівняння дробових чисел (`double`) виконується з дельтою (наприклад, `0.001`), а підсумкові розрахунки враховують шкалу та округлення. |
| **CR-06** | **Повна ізоляція та незалежність тестів** | Тести не залежать від черговості виконання або глобального стану; очищення та ініціалізація виконуються в `@BeforeEach`. UI-тести самі керують життєвим циклом браузера. |
| **CR-07** | **Якість UI-тестів (відсутність сліпів, стійкі селектори)** | У UI-тестах суворо заборонено `Thread.sleep` та неявні очікування (`implicitlyWait`). Використовується `WebDriverWait` (ExpectedConditions). Локатори базуються на ID, іменах, data-атрибутах; абсолютні XPath неприпустимі. |
| **CR-08** | **Коректне поводження з падіннями та відсутність `@Disabled`** | Тест, що падає на версії v1, зобов'язаний відповідати задокументованому звіту про дефект (`MOD-BUG-...`) у трекері з обов'язковим посиланням у коментарі. Необґрунтовані `@Disabled` відсутні. |

  - *Відповідь автора (Володимир Костенко & Олександр Пархоменко):*
    Зауваження прийнято! Додали детальні javadoc-коментарі з ID дефектів `MOD-BUG-001` та `MOD-BUG-002`, посилання на трекер та обґрунтування відповідно до розділу 12 рекомендацій методички.
