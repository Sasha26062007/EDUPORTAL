### Питання 1. Що таке автоматизоване тестування і які кроки тесту воно виконує без участі людини?
**Відповідь:**  
**Автоматизоване тестування** — це процес верифікації програмного забезпечення за допомогою спеціальних програмних засобів та скриптів, які виконують тестові сценарії без прямої участі людини та порівнюють фактичні результати з очікуваними.  
Автотест автоматично виконує всі 4 ключові кроки життєвого циклу тесту:
1. **Підготовка передумов та середовища (Setup / Arrange):** створення об'єктів, підготовка тестових даних, відкриття з'єднання чи браузера.
2. **Виконання тестової дії (Execution / Act):** виклик цільового методу, надсилання запиту або взаємодія з елементами UI (клік, введення тексту).
3. **Звірка результату з очікуваним (Verification / Assert):** перевірка фактично отриманого значення, стану чи винятку на відповідність вимогам специфікації.
4. **Очищення ресурсів (Teardown / Cleanup):** закриття браузера, скидання стану, звільнення пам'яті.

### Питання 2. Для яких методів пишуть юніт-тести і як юніт-тести пов'язані з регресійним тестуванням?
**Відповідь:**  
- **Юніт-тести пишуть для:**  
  Методів, що містять **нетривіальну бізнес-логіку**: розрахунки, математичні алгоритми, розгалуження (`if/else`, `switch`), валідацію вхідних даних, роботу з межами діапазонів, перетворення форматів даних та генерацію винятків.  
  *Не пишуть юніт-тести на:* тривіальні геттери/сеттери без логіки, стандартні конструктори записів (`record`) або стандартні методи сторонніх бібліотек.
- **Зв'язок із регресійним тестуванням:**  
  Юніт-тести утворюють фундамент регресійного тестування («захисну сітку»). При будь-якій зміні вихідного коду (рефакторинг, виправлення багів, оптимізація) повторний прогін набору юніт-тестів (`mvn test`) за лічені секунди гарантує, що нові зміни не зламали раніше реалізовану поведінку системи.

### Питання 3. Що означають три частини тесту arrange — act — assert? Наведіть приклад для одного правила вашого модуля.
**Відповідь:**  
Патерн **AAA (Arrange — Act — Assert)** — це стандарт структурування тіла модульного тесту:
- **Arrange (Підготовка):** ініціалізація тестованого екземпляра, створення вхідних параметрів та налаштування очікувань.
- **Act (Дія):** безпосередній виклик одного досліджуваного методу з підготовленими даними.
- **Assert (Перевірка):** твердження, що перевіряє рівність отриманого результату або генерацію винятку.

**Приклад для правила BL-40 нашого модуля (`QuizScorer`):**
```java
@Test
@DisplayName("BL-40: правильна відповідь на питання з 1 варіантом дає рівно 1.0 бал")
void questionScoreSingleChoiceCorrectReturnsOne() {
    // 1. Arrange: готуємо питання q1 з правильною відповіддю 'B'
    QuizQuestion q = new QuizQuestion("q1", Set.of("A", "B", "C"), Set.of("B"));

    // 2. Act: студент обирає варіант 'B'
    double score = scorer.questionScore(q, Set.of("B"));

    // 3. Assert: перевіряємо, що нараховано рівно 1.0 бал
    assertEquals(1.0, score, 0.001);
}
```

### Питання 4. Навіщо потрібен `@BeforeEach` і чим він відрізняється від `@BeforeAll`?
**Відповідь:**  
- **`@BeforeEach`** виконується перед **кожним окремим тестовим методом** у класі. Він гарантує, що кожен тест отримує новий, чистий та ізольований екземпляр тестованого об'єкта, унеможливлюючи вплив тестів один на одного (дотримання принципу незалежності F.I.R.S.T.).
- **Відмінності від `@BeforeAll`:**
  - `@BeforeAll` виконується **лише один раз перед усіма тестами** класу (метод за замовчуванням має бути `static`).
  - `@BeforeAll` використовується для важких ресурсомістких одноразових операцій (наприклад, запуск локального веб-сервера чи підключення до тестової БД).
  - У `@BeforeEach` створюються змінні екземпляра, які кожен тест може змінювати без ризику впливу на наступні тести.

### Питання 5. Чим `@ParameterizedTest` із `@CsvSource` кращий за п'ять окремих методів `@Test`?
**Відповідь:**  
1. **Усунення дублювання коду (DRY):** тіло тесту (підготовка та твердження) записується один раз, а набір тестових даних передається як таблиця аргументів.
2. **Краща деталізація у звітах:** JUnit виконує кожний рядок `@CsvSource` як окремий підтест із власним відображенням вхідних параметрів. Якщо падає одне граничне значення (наприклад, 95.0), інші залишаються зеленими, і розробник одразу бачить точну межу дефекту.
3. **Легкість розширення тест-кейсу:** для додавання нової граничної точки (BVA) достатньо дописати один рядок у таблицю, не створюючи новий метод.

### Питання 6. Як перевірити, що метод кидає виняток, і чому `try/catch` у тесті гірший?
**Відповідь:**  
- **Правильний спосіб у JUnit 5:**  
  Використання методу `assertThrows(ExpectedException.class, () -> executable)`:
  ```java
  assertThrows(IllegalArgumentException.class, () -> scorer.score(Map.of(), Collections.emptyList()));
  ```
- **Чому `try/catch` гірший:**
  1. *Ризик хибнопозитивного проходження:* якщо метод **не викине виняток**, блок `catch` просто не виконається, і тест помилково вважатиметься успішним (якщо розробник забув написати `fail("Очікувався виняток")` після виклику).
  2. *Громіздкість коду:* `try/catch/fail` вимагає 6–8 рядків бойлерплейту замість одного компактного рядка `assertThrows`.
  3. *Читабельність:* `assertThrows` повертає екземпляр винятку, що дозволяє додатково перевірити повідомлення про помилку через `assertEquals("...", ex.getMessage())`.

### Питання 7. Чим `assertAll` відрізняється від послідовності окремих `assertEquals`?
**Відповідь:**  
- **Послідовність окремих `assertEquals`:** має поведінку **Fail-Fast**. Якщо перше твердження падає, виконання методу негайно переривається викидом `AssertionError`, а решта перевірок навіть не виконуються. Розробник не знає, чи пройшли б наступні перевірки.
- **`assertAll` (Soft Assertions):** виконує **всі передані лямбда-вирази** незалежно від того, чи впали попередні, збирає всі знайдені невідповідності та виводить їх у консоль єдиним зведеним звітом. Це критично важливо для перевірки пов'язаних властивостей одного об'єкта.

### Питання 8. Тест упав. Які дії ви робите перед тим, як виправляти тест або писати звіт про дефект?
**Відповідь:**  
Перед будь-якими змінами виконується суворий алгоритм із 4 кроків:
1. **Звірка зі специфікацією (SRS / BL-вимогою):** відкриваємо офіційну вимогу та перечитуємо формулювання правила.
2. **Ручний незалежний перерахунок:** обчислюємо очікуване значення вручну (на калькуляторі) за формулою з вимоги, не дивлячись у реалізацію коду.
3. **Аналіз очікуваного значення в тесті:**  
   - Якщо в тесті була допущена описка або неправильно розрахована формула — це помилка тесту, виправляємо тест.
   - Якщо тест точно відповідає вимозі SRS, а код модуля видає інше значення — **це дефект модуля**.
4. **Фіксація дефекту:** реєструємо звіт про дефект у трекері (`docs/module-defects.md` / GitHub Issues) з міткою `module`, а тест залишаємо «червоним» у тестовому наборі до Спринту 5. Підганяти очікуване під код категорично заборонено!

### Питання 9. Чим `assert...` відрізняється від `verify...` у Selenium IDE і що є їх аналогами у JUnit 5?
**Відповідь:**  
- **У Selenium IDE:**
  - `assert...` (наприклад, `assertText`, `assertElementPresent`) — це **Hard Assertion**: якщо перевірка не виконується, виконання всього сценарію негайно зупиняється (тест абортується).
  - `verify...` (наприклад, `verifyText`) — це **Soft Assertion**: якщо перевірка впала, помилка логується у звіті, але сценарій продовжує виконувати наступні кроки.
- **Аналоги у JUnit 5:**
  - Аналог `assert...` — звичайні статичні методи класу `Assertions.*` (`assertEquals`, `assertTrue`).
  - Аналог `verify...` — використання групування `assertAll(...)` або спеціалізованих бібліотек `SoftAssertions` (AssertJ).

### Питання 10. Що робить Selenium Manager і чому у стартовому проєкті немає файлу chromedriver?
**Відповідь:**  
- **Selenium Manager** — це вбудований у Selenium 4.6+ автоматичний бінарний інструмент керування драйверами (розроблений на мові Rust).
- **Принцип роботи:** під час запуску тесту він автоматично визначає тип і точну версію встановленого у системі браузера (наприклад, Google Chrome v128), перевіряє наявність сумісного драйвера у локальному кеші (`~/.cache/selenium`), а за його відсутності самостійно завантажує сумісний бінарник `chromedriver` з офіційного репозиторію та додає його у `PATH` процесу.
- **Чому немає файлу `chromedriver` у репозиторії:** завдяки Selenium Manager відпала потреба вручну скочувати драйвери під кожну ОС (Windows, Linux, macOS) та комітити застарілі `.exe` файли у Git.

### Питання 11. Який локатор найстійкіший до змін сторінки і чому? Який — найгірший?
**Відповідь:**  
- **Найстійкіший локатор:**  
  1. Спеціалізовані тестові data-атрибути: `By.cssSelector("[data-testid='submit-btn']")` або `[data-qa='...']`. Вони створюються виключно для автотестів і не змінюються фронтенд-розробниками під час редизайну.
  2. Унікальний статичний атрибут `By.id("username")` або `By.name("password")`.
- **Найгірший локатор:**  
  **Абсолютний XPath** (повний шлях від кореня DOM), наприклад:  
  `/html/body/div[2]/div[1]/section/div/div[3]/form/button[1]`.  
  *Чому найгірший:* він надзвичайно крихкий (fragile/brittle). Будь-яка зміна верстки (додавання рекламного банера, обгортання у новий `<div>`, зміна структури меню) миттєво ламає весь шлях, і тест падає з `NoSuchElementException`.

### Питання 12. Навіщо `WebDriverWait`, якщо можна написати `Thread.sleep(2000)`?
**Відповідь:**  
`Thread.sleep(2000)` — це найгірший антипатерн в автоматизації UI-тестування:
1. **Штучне уповільнення тестів:** `Thread.sleep` змушує потік безумовно простоювати зазначені мілісекунди, навіть якщо елемент став доступним вже через 50 мс. При наборі зі 100 тестів прогін затягується на десятки хвилин.
2. **Нестабільність і флакування (Flaky Tests):** якщо через мережеву затримку чи навантаження на сервер елемент з'явиться на 2001-й мілісекунді — тест впаде, хоча застосунок справний.
3. **Переваги `WebDriverWait` (явні очікування):**
   - Працює за принципом інтелектуального опитування DOM (кожні 500 мс) до настання конкретної очікуваної умови (`visibilityOfElementLocated`, `elementToBeClickable`).
   - Як тільки елемент готовий — тест продовжує виконання миттєво.
   - Якщо умова не наступила протягом таймауту (наприклад, 10 с) — викидається інформативний `TimeoutException`.

## Частина 2. Спеціалізовані питання для Скрам-майстра / Рецензента (Reviewer)

### Питання 13. Які ключові антипатерни в юніт-тестах зобов'язаний виявляти рецензент під час Code Review (§5.3)?
**Відповідь:**  
Під час рев'ю рецензент контролює відсутність таких антипатернів:
1. **The Liar (Підігнаний тест):** очікуване значення в тесті замінено під некоректний вивід програми v1 заради «зеленого» статусу білду.
2. **Sleepy Test:** використання `Thread.sleep` замість явних очікувань у UI-тестах.
3. **Happy Path Only:** відсутність перевірки винятків (`assertThrows`) та некоректних аргументів.
4. **Boundary Blindness:** перевірка границі лише однією точкою замість трьох ($N-\Delta, N, N+\Delta$).
5. **Secret Catcher:** порожній блок `catch (Exception e) {}`, який ковтає винятки і маскує реальні помилки.
6. **Unmotivated `@Disabled`:** вимкнення тестів, що падають, замість реєстрації баг-репорту.

### Питання 14. Як відрізнити «підігнаний тест» (Test Fitting) від правильного тесту?
**Відповідь:**  
- **Ознака підігнаного тесту:** розробник бере значення з виводу консолі чи екцепшена і вставляє його в `assertEquals` («раз код повертає 72.9, напишу 72.9»).
- **Ознака правильного тесту:** очікуване значення виводиться виключно з тексту бізнес-вимоги SRS незалежно від реалізації. Якщо вимога говорить «лінійний штраф 10% за день, 3 дні = 30%», то для 100 балів очікується строго 70.0 балів. Якщо код v1 повертає 72.9 — тест **зобов'язаний вимагати 70.0 і падати**!

### Питання 15. Як Денис Бучинський реалізував свій персональний внесок у тестову базу проєкту?
**Відповідь:**

6. `scoreAttemptStandardCalculation()` — підсумок спроби 100% при всіх правильних відповідях (BL-60).
